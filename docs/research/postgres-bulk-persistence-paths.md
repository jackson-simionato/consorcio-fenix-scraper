# PostgreSQL bulk persistence paths for `RouteSnapshot` ingestion

## Question and constraints

Which PostgreSQL-specific persistence path is most likely to reduce a representative cold write from 627.59 seconds to at most 156.90 seconds without changing version history, uniqueness rules, indexes, the advisory read contract, or read availability?

This note evaluates the repository at SQLAlchemy 2.0.49, GeoAlchemy2 0.19.0, and psycopg 3.3.4 (the versions in `uv.lock`). The representative cold run contains 186 routes, 353 **Route Directions**, about 97,000 **Materialized Route Segments**, 14,800 schedule entries, and 4,300 itinerary steps. The locked design also requires batch commits, retention of completed batches after a later failure, an unchanged-run time no worse than 110% of baseline, stable CLI stdout, and structured persistence timings.

## Finding

The best prototype order is:

1. Replace per-route lookup/update/flush cycles with set-oriented prefetches, PostgreSQL upserts, client-assigned UUIDs, and Core/ORM bulk DML.
2. Use SQLAlchemy bulk `INSERT` for low- and medium-volume child tables.
3. Compare SQLAlchemy bulk `INSERT` with direct psycopg `COPY FROM STDIN` for `route_segments`; keep text staging plus a typed `INSERT ... SELECT` as a fallback if direct geometry adaptation does not preserve the current values.
4. Start with one database writer. Test a small, bounded pool of writers only if a single writer remains latency-bound and the database has measured spare capacity.

This order matters because SQLAlchemy 2 can apply `insertmanyvalues` to PostgreSQL unit-of-work flushes and bulk executions when batched `RETURNING` is needed, including correlation for client-generated UUID primary keys; the existing code is therefore not necessarily issuing one `INSERT` round trip per child row. SQLAlchemy documents a default page size of 1,000 rows subject to a 32,700-parameter ceiling ([SQLAlchemy `insertmanyvalues`](https://docs.sqlalchemy.org/en/20/core/connections.html#engine-insertmanyvalues)). In the installed PostgreSQL dialect, `use_insertmanyvalues` is enabled but `use_insertmanyvalues_wo_returning` is disabled, so executions without `RETURNING` may instead use the driver's executemany behavior. Psycopg 3.1 and newer pipelines `executemany()` internally ([psycopg pipeline mode](https://www.psycopg.org/psycopg3/docs/advanced/pipeline.html)). The benchmark must measure actual emitted statements and round trips before attributing all 627.59 seconds to row-at-a-time inserts.

The current implementation still has two clear scaling costs independent of that automatic batching:

- It performs route, fare-version, and route-version reads/updates inside the 186-route loop, making remote round trips scale with route count.
- It constructs roughly 97,000 instrumented `RouteSegmentRecord` objects, retains them in a `Session` until flush, and flushes between dependency layers to discover generated foreign keys. SQLAlchemy describes the `Session` as an instrumented identity-map/unit-of-work layer and notes that queries trigger autoflush of pending changes ([Session basics and flushing](https://docs.sqlalchemy.org/en/20/orm/session_basics.html#flushing)).

Client-assigned UUIDs remove the flush dependency: assign every route, version, **Route Direction**, **Service Direction**, **Materialized Route Segment**, schedule-entry, and itinerary-step identifier while materializing a batch. SQLAlchemy's `Uuid(as_uuid=True)` expects Python `uuid.UUID` objects, matching the existing model ([SQLAlchemy `Uuid`](https://docs.sqlalchemy.org/en/20/core/type_basics.html#sqlalchemy.types.Uuid)). SQLAlchemy also invokes a Python column default once per parameter set in multi-row execution, but explicit UUID assignment is preferable here because rows sent through raw psycopg `COPY` do not pass through SQLAlchemy's Python defaults ([SQLAlchemy defaults](https://docs.sqlalchemy.org/en/20/core/defaults.html#context-sensitive-default-functions)).

## Path comparison

| Path | What it improves | Semantics and risks | Role in the prototype |
| --- | --- | --- | --- |
| Current ORM unit of work, with fewer explicit flushes | Keeps mapped types and existing persistence behavior; PostgreSQL can already use `insertmanyvalues` during flush. | Still pays ORM construction/tracking cost and cannot remove the per-route `SELECT`/`UPDATE` pattern by itself. Actual batching must be confirmed in SQL logs because page and parameter limits split large inserts into multiple statements ([SQLAlchemy `insertmanyvalues`](https://docs.sqlalchemy.org/en/20/core/connections.html#engine-insertmanyvalues)). | Baseline/control, not the expected final path. |
| `Session.execute(insert(Model), list[dict])` or Core `Connection.execute(table.insert(), list[dict])` | Avoids constructing persistent child objects while retaining SQLAlchemy type processing, transaction integration, statement logging, and batched insert support. Bulk `INSERT ... RETURNING` is supported on PostgreSQL, but returned order is not guaranteed unless `sort_by_parameter_order=True` is requested ([SQLAlchemy bulk INSERT](https://docs.sqlalchemy.org/en/20/orm/queryguide/dml.html#orm-bulk-insert-statements)). | Ordered `RETURNING` may constrain batching on some backends. This design should instead correlate results by an explicit UUID or natural key, so it does not depend on return order. Heterogeneous parameter dictionaries may be split into groups; build uniform dictionaries per table. | Default for **Route Directions**, **Service Directions**, schedule entries, and itinerary steps; first candidate for **Materialized Route Segments**. |
| PostgreSQL `INSERT ... ON CONFLICT` | Collapses select-then-insert/update races and supports set-based route, fare-version, and route-version reconciliation. PostgreSQL guarantees an atomic insert-or-update outcome for `DO UPDATE`, and `RETURNING` exposes rows actually inserted or updated ([PostgreSQL `INSERT`](https://www.postgresql.org/docs/current/sql-insert.html#SQL-ON-CONFLICT)). SQLAlchemy exposes both `on_conflict_do_nothing()` and `on_conflict_do_update()` ([SQLAlchemy PostgreSQL upsert](https://docs.sqlalchemy.org/en/20/dialects/postgresql.html#insert-on-conflict-upsert)). | `DO UPDATE` locks/updates conflicting rows even when little changes, while `DO NOTHING RETURNING` returns only inserted rows. SQLAlchemy's Python `onupdate` defaults are not applied automatically inside `on_conflict_do_update`, so every changed column must be explicit ([SQLAlchemy PostgreSQL upsert](https://docs.sqlalchemy.org/en/20/dialects/postgresql.html#the-set-clause)). | Use for natural-key reconciliation, paired with one canonical-ID query where `DO NOTHING` encounters existing rows. |
| psycopg `COPY FROM STDIN` directly to final tables | Uses PostgreSQL's bulk copy protocol; psycopg calls it one of the most efficient load paths. Row-wise `write_row()` adapts ordinary Python values and the operation remains part of the normal transaction, so it can be committed or rolled back ([psycopg COPY](https://www.psycopg.org/psycopg3/docs/basic/copy.html)). | `COPY` has no `ON CONFLICT` or `RETURNING` clause. A unique violation fails the command. PostgreSQL invokes destination triggers and check constraints, and a failed large copy can leave invisible dead tuples until vacuum ([PostgreSQL `COPY`](https://www.postgresql.org/docs/16/sql-copy.html#SQL-COPY-NOTES)). Direct geometry copy bypasses GeoAlchemy2's bind expression, but PostGIS accepts EWKT as canonical text input for insert, update, and copy ([PostGIS canonical forms](https://postgis.net/docs/manual-3.4/using_postgis_dbmanagement.html#EWKB_EWKT)). | Reject for natural-key tables; first COPY candidate for known-new `route_segments` with explicit IDs and normalized geometry checks. |
| psycopg `COPY` to a temporary staging table, then typed `INSERT ... SELECT` | Keeps the fast transport path while allowing explicit geometry conversion and ordinary final-table constraints. Set-based final insertion can be timed separately from transfer/index maintenance. | Adds temporary-table setup and a second server-side write. The final `INSERT` remains responsible for all target constraints and indexes. The staging table and final insert must be inside the same batch transaction. | Fallback if direct COPY adaptation is incorrect or unacceptably fragile; also an experiment for other very high-volume children only if their Core results justify it. |
| Bounded parallel writers | Separate connections can overlap database operations; psycopg notes that commands on one connection are serialized, while multiple connections permit parallel operations ([psycopg concurrency](https://www.psycopg.org/psycopg3/docs/advanced/async.html#concurrent-operations)). | Workers that update the same route/fare/current rows can wait on row locks; row locks last to transaction end and deadlocks are possible ([PostgreSQL row locking](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS)). Extra connections can reduce rather than improve server throughput. | Optional last experiment, bounded by the SQLAlchemy pool and partitioned by route code; never the first optimization. |

## Set-oriented persistence shape

A prototype can preserve the current schema and behavior with the following data flow:

1. Materialize one row-weighted batch in Python and assign UUIDs to every proposed row before opening dependency-layer inserts.
2. Prefetch all existing `routes` by `code` and all relevant `fare_versions` by `(region, source_hash)` in one query per table. Upsert missing/current metadata in set-oriented statements and retain a map from natural keys to canonical database IDs.
3. Prefetch existing `route_versions` by `(route_id, source_hash, map_hash)` using PostgreSQL null-safe equality for `map_hash`. For each affected route, set previous versions non-current in one set-based update, insert proposed versions with the named uniqueness rule, and mark the canonical selected versions current.
4. Treat only versions successfully inserted in this batch as new. Existing versions reuse their canonical database UUID and receive no children. This preserves the current invariant that unchanged `RouteSnapshot` inputs never duplicate **Route Directions**, **Materialized Route Segments**, schedule entries, or itinerary steps.
5. Build **Route Direction** and **Service Direction** rows with preassigned UUIDs, then build all dependent rows without intermediate flushes. Send uniform parameter dictionaries table by table.
6. Commit the route set as one batch. An exception rolls back only that batch; a fresh transaction records run failure after the failed transaction is gone.

For conflict handling, do not assume the proposed UUID is canonical when `ON CONFLICT DO NOTHING` fires: PostgreSQL returns only rows actually inserted or updated ([PostgreSQL `RETURNING`](https://www.postgresql.org/docs/current/dml-returning.html)). Either use an explicit `DO UPDATE ... RETURNING id` where a real update is required, or combine `DO NOTHING RETURNING` for inserted keys with one follow-up query that maps every conflicting natural key to its stored ID. Avoid depending on the order of returned rows; SQLAlchemy explicitly says bulk `RETURNING` order is not guaranteed unless ordered correlation is requested ([SQLAlchemy bulk `RETURNING`](https://docs.sqlalchemy.org/en/20/orm/queryguide/dml.html#getting-new-objects-with-returning)).

## Geometry encoding

The repository currently passes EWKT-like strings such as `SRID=4326;LINESTRING(...)` to `Geometry("LINESTRING", srid=4326)`. GeoAlchemy2's `Geometry` type wraps bound values in `ST_GeomFromEWKT`, while its bind processor converts `WKTElement` values to EWKT ([GeoAlchemy2 spatial types](https://geoalchemy-2.readthedocs.io/en/stable/types.html#geoalchemy2.types.Geometry)). Core or ORM bulk inserts through the mapped/table type therefore preserve the existing conversion path.

Raw psycopg `COPY` bypasses that GeoAlchemy2 bind expression. PostGIS nevertheless defines EWKT as canonical ASCII input guaranteed to be accepted by simple insert, update, or copy operations ([PostGIS canonical forms](https://postgis.net/docs/manual-3.4/using_postgis_dbmanagement.html#EWKB_EWKT)). The first COPY comparison should therefore send the existing `SRID=4326;LINESTRING(...)` strings directly to the final geometry column with explicit UUIDs. It must verify normalized geometry and SRID equality against the SQLAlchemy path.

If direct `write_row()` adaptation is incorrect or too fragile, use the safer fallback without introducing Shapely or a custom psycopg PostGIS adapter:

- Copy the existing `SRID=4326;LINESTRING(...)` value into a temporary staging `text` column.
- Insert into the final geometry column with an explicit `ST_GeomFromEWKT(staging.geometry_text)` expression.
- Keep SRID 4326 and longitude/latitude order unchanged, and verify geometry equality with the existing normalized read tests.

Do not start with binary COPY. Psycopg warns that binary COPY applies no casts and requires correct binary dumpers/types for every value; `Copy.set_types()` may be required ([psycopg binary COPY](https://www.psycopg.org/psycopg3/docs/basic/copy.html#binary-copy)). Text COPY is easier to validate against the current GeoAlchemy2 semantics, with text staging available if direct type input proves unreliable. A later EWKB experiment is possible because GeoAlchemy2 exposes WKB/EWKB elements, but it should earn its added encoding complexity in the benchmark ([GeoAlchemy2 elements](https://geoalchemy-2.readthedocs.io/en/stable/elements.html)).

## Transaction, error, and concurrency behavior

The current CLI wraps the entire call in `session_factory.begin()`, so all routes share one transaction. The locked batch requirement needs a transaction per persistence batch rather than savepoints within one outer transaction: SQLAlchemy documents that a transaction context commits on success and rolls back on exception, while a failed flush leaves the `Session` unusable until rollback ([SQLAlchemy transaction framing](https://docs.sqlalchemy.org/en/20/orm/session_transaction.html#managing-transactions), [flush failure behavior](https://docs.sqlalchemy.org/en/20/orm/session_basics.html#flushing)). psycopg COPY participates in the same transaction; an exception inside its context discards the COPY rows, and the surrounding transaction can be rolled back ([psycopg COPY transaction behavior](https://www.psycopg.org/psycopg3/docs/basic/copy.html#using-copy-to-and-copy-from)).

Each batch should use one fresh `Session`/connection transaction. The durable `scrape_runs` lifecycle needs separate short control transactions so `RUNNING`, `FAILED`, and `finished_at` survive a data-batch rollback; the exact interface belongs to the later lifecycle-design ticket. Within a batch, update `is_current` and insert the replacement version in the same transaction so readers see either the old or new route state, never an uncommitted intermediate state.

PostgreSQL MVCC allows ordinary readers and writers to proceed without blocking each other ([PostgreSQL MVCC](https://www.postgresql.org/docs/current/mvcc-intro.html)). This preserves advisory read availability without dropping constraints or indexes. It does not eliminate writer/writer contention: route and fare upserts plus `is_current` updates can lock shared rows until commit ([PostgreSQL row locking](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS)). If parallel writes are tested, use one connection per worker because psycopg serializes work sharing a connection and shares that connection's transaction/error state across cursors ([psycopg concurrency](https://www.psycopg.org/psycopg3/docs/advanced/async.html#concurrent-operations)). Start at two workers, cap workers and pool size together, partition routes deterministically, and record lock waits/deadlocks.

## Compatibility constraints

- Preserve the named unique constraints on routes, fare versions, route versions, **Service Directions**, and **Materialized Route Segments**. The route-version constraint uses `NULLS NOT DISTINCT`; that syntax requires PostgreSQL 15 or newer and makes null `map_hash` values conflict as intended ([PostgreSQL 15 `CREATE TABLE`](https://www.postgresql.org/docs/15/sql-createtable.html)).
- Preserve all foreign keys and existing B-tree/GiST indexes. Do not speed a benchmark by disabling or dropping them; the roughly 97,000-**Materialized Route Segment** cost must include the production target schema.
- Preserve the stable advisory fields and current-route filters. Batch transactions may make completed batches visible, but no committed route may temporarily have zero current versions.
- Preserve UUID values as Python `uuid.UUID` instances for SQLAlchemy paths. For COPY, provide explicit IDs because SQLAlchemy's client defaults are not involved.
- Preserve JSON/JSONB payload shapes. Core inserts through the SQLAlchemy table retain JSON type processing; raw COPY would need explicit JSON serialization and should not be introduced unless measured.
- Use SQLAlchemy's already-owned connection when invoking psycopg COPY so Core statements and COPY share one transaction. SQLAlchemy documents access through `Connection.connection` and recommends keeping transaction control on the owning `Connection` ([SQLAlchemy raw DBAPI access](https://docs.sqlalchemy.org/en/20/core/connections.html#working-with-driver-sql-and-raw-dbapi-connections)).

## Falsifiable expectations for the benchmark ticket

These are prototype gates, not claims about unmeasured production performance:

1. **Set-oriented metadata gate:** For a 186-route cold batch, route/fare/version reconciliation should have statement count proportional to tables and chunks, not routes. Expect at least an 80% reduction from the measured metadata SQL statement count. Reject the design if statement count still scales linearly because of hidden autoflushes or per-route lookups.
2. **Client/ORM overhead gate:** Core parameter dictionaries with explicit UUIDs should eliminate `RouteSegmentRecord` construction and intermediate dependency flushes. Expect at least a 30% reduction in Python-side materialization-plus-flush time and lower peak allocations. If database execution dominates and this gain is below 10% of total persistence time, keep the simpler SQLAlchemy path.
3. **Core bulk gate:** With indexes and constraints enabled, Core/ORM bulk `INSERT` should bring total cold persistence materially closer to the 156.90-second ceiling. Keep it over COPY if it meets the ceiling and 25%-of-baseline target, because it has the smallest type/transaction surface change.
4. **COPY gate:** Test direct COPY only for `route_segments`, the roughly 97,000-row dominant table, then test staging only if direct adaptation fails correctness. Promote a COPY path only if it is at least 20% faster than tuned Core bulk insert and the whole cold run meets both target thresholds. Otherwise the extra raw-driver path is not justified.
5. **Unchanged-run gate:** Bulk prefetch must identify all existing versions before child materialization, write zero child rows, create zero duplicate versions, and finish within 110% of its measured unchanged baseline.
6. **Parallelism gate:** Try two writers only after the best single-writer design. Keep parallelism only if median total persistence improves by at least 20% across three runs with no deadlocks, no meaningful lock-wait regression, identical normalized data, and unchanged reader availability. Otherwise use one writer.
7. **Failure gate:** Inject an error in the first, middle, and final batch. Only the active batch may roll back; earlier committed batches must remain queryable/reusable, the run must be durably failed, and a retry must not create duplicate versions or children.

The feedback loop should report separate medians for Python materialization, metadata reconciliation, each child-table write, COPY transfer, typed staging merge, commit, total statements, rows, and rows/second. SQLAlchemy's `insertmanyvalues` batches are visible to statement logging and cursor events, so the loop can distinguish compilation, execution, and batch count without guessing ([SQLAlchemy logging for `insertmanyvalues`](https://docs.sqlalchemy.org/en/20/core/connections.html#logging-and-events)).
