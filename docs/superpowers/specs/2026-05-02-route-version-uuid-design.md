# Route Version Deduplication and UUID IDs Design

## Goal

Route version history must record each distinct scraped route snapshot once. Re-running the scraper against unchanged route page and map content must not create duplicate `route_versions` rows or duplicate child records.

The project must also use UUID primary and foreign keys consistently for persisted entities instead of mixing integer and string identifiers.

## Version Identity

A route version is uniquely identified by:

- `route_id`
- `source_hash`
- `map_hash`

`source_hash` represents the canonical route page content. `map_hash` represents the KML/map content and may be null when no map content exists. A change to either hash creates a new historical version. If both hashes match an existing version for the same route, the existing version is reused.

## Database Schema

All database entity primary keys become PostgreSQL UUID columns generated by the application with `uuid4`:

- `scrape_runs.id`
- `routes.id`
- `route_versions.id`
- `route_directions.id`
- `schedule_entries.id`
- `itinerary_steps.id`
- `stops.id`
- `raw_pages.id`

Foreign key columns that reference these IDs also become UUIDs. Non-identity numeric fields, such as `fare_cents` and sequence numbers, remain integers.

`route_versions` gets a PostgreSQL null-aware uniqueness constraint over `route_id`, `source_hash`, and `map_hash`. The implementation will use `NULLS NOT DISTINCT` behavior so routes without map content are also protected from duplicates at the database level. The persistence lookup must still compare `map_hash` null-safely before inserting, so normal runs reuse existing rows without relying on an integrity error.

## Persistence Behavior

When persisting a route snapshot:

1. Find or create the route by `code`.
2. Update current route metadata from the latest snapshot.
3. Look for an existing `route_versions` row for the same route with matching `source_hash` and `map_hash`, including null-safe `map_hash` comparison.
4. If an existing version is found:
   - Mark other versions for the route as not current.
   - Mark the matching version as current.
   - Do not insert a new version.
   - Do not insert child route directions, schedule entries, or itinerary steps.
5. If no matching version exists:
   - Mark existing route versions for the route as not current.
   - Insert the new route version.
   - Insert child directions, schedules, and itinerary steps for that new version.

Every scrape still creates its own `scrape_runs` row. Reused route versions keep their original `scrape_run_id`, preserving the run that first observed that version.

## Code Changes

SQLAlchemy models will import `uuid` and PostgreSQL `UUID`, define a shared helper for UUID primary key columns, and update mapped ID types to `uuid.UUID`.

Domain models that expose persisted IDs will use `uuid.UUID | None`. Route parser and scraper business data remain unchanged because route codes and external source values are not database identity IDs.

The initial Alembic migration will be updated to create UUID columns directly, which matches the project state: a single early schema migration and no separate production migration history in the repository.

## Testing

Add focused persistence tests that exercise the behavior without requiring a live PostGIS database where possible:

- Persisting the same route snapshot twice with the same `source_hash` and `map_hash` creates only one route version.
- Persisting a changed `source_hash` creates a second route version.
- Persisting a changed `map_hash` creates a second route version.
- UUID mapped IDs are generated as `uuid.UUID` values.

Existing tests for geometry formatting and parsing must continue to pass.
